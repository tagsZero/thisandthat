사용자는 브라우저에서 URL로 접속한다. Python·DB·PDF용 Chromium은 서버에서 실행하며 사용자 PC에 설치를 요구하지 않는다. 첫 구성은 AWS의 Ubuntu 24.04 서버 한 대에 웹 애플리케이션과 PostgreSQL, Chromium을 함께 둔다.

| Flask 서버 | 로그인 세션, 대시보드 조회, 일정 처리, 입력 확인, Decimal 분류, 해석 조회·저장 |
| PostgreSQL | 기본 계정, 일정, 전문가 자료와 해석 조건, 현재 보고서 데이터 |

Flask는 로그인·두 대시보드와 보고서 작성 세 단계의 화면·데이터 요청을 한 애플리케이션에서 제공한다. 목록·입력표·선택문·보고서 중심이므로 Jinja2와 기본 JavaScript로 구현한다. React와 Node.js 빌드 과정은 초기 구성에 포함하지 않는다.

## 화면과 요청 처리

별도 프런트엔드 서버를 만들지 않는다. 일반 페이지는 Flask와 Jinja2로 표시하고, 분류 변경·후보 조회·선택 내용 미리보기에는 작은 JavaScript 요청을 사용한다. 서버가 분류와 후보 조회 결과를 계산한다.

경계 변경은 브라우저가 점수와 설정을 보내고 서버가 H/M/L·유형·후보를 반환하는 흐름이다. 선택·순서·문장 수정은 브라우저에서 즉시 반영하고 저장 시 서버로 보낸다. 분류 계산을 브라우저와 서버에 각각 구현하지 않는다. 빠르게 기준을 바꿨을 때는 마지막 요청의 결과만 화면에 적용한다. 이 방식은 Flask의 [JavaScript와 fetch 안내](https://flask.palletsprojects.com/en/stable/patterns/javascript/)를 따른다.

전체 프로파일·유형·후보·저장 기준 대비 차이는 같은 요청 맥락의 결과로 표시한다. 조회 결과가 현재 입력 기준과 일치할 때만 화면에 적용한다. 조회 실패나 유효하지 않은 기준에서는 마지막 유효 결과와 현재 입력의 차이를 알리고 작성 내용은 유지한다.

두 배치는 하나의 작성 상태를 공유하고 배치·탭·현재 척도 같은 화면 위치를 검사·보고서 데이터와 분리한다. 배치만 전환할 때 서버 조회·분류·보고서 저장을 실행하지 않는다. 브라우저에는 마지막 배치 값만 기억하며 검사정보나 별도 초안 DB를 추가하지 않는다.

메뉴, 분류 계산, 자료 조회, 보고서 조립은 역할을 나누되 한 애플리케이션 안에서 구현한다. 범용 플러그인 플랫폼, 마이크로서비스와 작업 큐는 만들지 않는다. 현재 파일·폴더의 역할은 [README](../../README.md)에 정리하며 후속 기능도 이 구조에 맞춰 연결한다.

선택한 보고서 데이터에서 웹 미리보기와 PDF용 HTML을 만든다. PDF는 저장된 보고서 본문과 같은 데이터를 사용한다. 화면 캡처를 보고서 본문 이미지로 붙이는 방식은 사용하지 않는다.

## 로그인과 대시보드 처리

계정 생성 명령과 웹 `/register`가 같은 users 테이블에 아이디와 비밀번호 해시를 저장하며 기존 계정을 덮어쓰지 않는다. 웹 가입은 세션 CSRF·필드 검증·중복/DB 오류 처리 후 로그인으로 이동하고 자동 로그인하지 않는다. 초대 코드 환경 설정은 [PLAT-05](04-platform.md#registration)를 따른다. 신규 테이블·라이브러리는 없다. 로그인은 Werkzeug로 검증하고 Flask 세션에는 계정 식별자를 두며 로그아웃 시 해제한다. 대시보드·TCI·자료 조회·PDF 요청은 로그인 여부를 확인한다. 비밀번호 찾기·조직별 권한 화면은 포함하지 않는다.

사이트 기본 주소는 로그인 상태에 따라 로그인 또는 통합 대시보드로 연결한다. 통합 대시보드의 TCI 링크는 TCI 대시보드를 연다. 새 점수 입력은 별도 진입 동작이다.

최근 검사 목록은 저장된 보고서를 최근 수정 순으로 조회하고 이름·관리번호·검사일 검색과 간단한 페이지 이동을 제공한다. 빠른 리뷰는 선택한 기록의 저장된 점수·기준·본문을 읽는다. 최신 해석자료로 다시 조립하지 않는다.

일정은 날짜·시간·제목·메모와 선택적인 보고서 연결을 저장한다. 한국 시간 기준으로 오늘·이번 주를 조회하고 등록·수정·삭제한다. Jinja2 목록과 기본 날짜·시간 입력으로 시작하며 별도 캘린더 서비스나 일정 전용 라이브러리를 추가하지 않는다.

## 두 유형의 통합 설명과 자동 본문

사용자가 제공한 자료의 통합54개는 **제공 자료 기반 해석 초안**으로 사용한다. 선택한 T기준의 기질/성격 코드와 맞는 본문을 각각 한 번 자동 포함한다. 검사판·성인 적용 근거 미확인과 unknown/reference 원값은 출처 사본에 보존하고, 그 사실만으로 이 통합 본문을 차단하지 않는다. 공식 성인용 검증 완료나 표준 규준으로 표시하지 않는다. 이 사용 규칙은 승인된 기존 통합54개에 한정하며 모든 참고자료를 자동 포함하도록 넓히지 않는다. 실제 점수의 필수 조건·명시적 연령/검사군 제한·비활성화·손상된 조건·다른 유형·비출력 비교는 계속 구분한다.

자동 사용 판정은 기존 TYPE-01 integration/common 키·family/code·활성 상태·실제 조건을 재사용해 계산한다. 모든 reference를 match로 바꾸거나 edition을 adult로 바꾸지 않는다. 원고를 하드코딩하거나 새 자격 테이블/초안 서비스/전역 상태 관리 체계를 추가하지 않는다. 후보 평가·자동 구성·서명된 당시 근거·표시·자료 점검 수치가 같은 새 판정을 사용하게 최소 연결한다. 등록 개수·자료 기반 자동 포함 가능 개수와 검사판 근거 확인 여부는 별도로 표시한다.

기존 분류·자료·보고서 구조로 현재 기질/성격 코드, 통합 설명, 다른 해석·차이·출처를 조회한다. 같은 내용을 정리한 통합 본문은 데이터로 준비하고 화면·함수에 유형별 원고를 하드코딩하지 않는다.

새 보고서 초안에는 통합 설명이 자동 포함된다. 기본 설명을 적용하기 위한 별도 명령·선택 API 동작을 만들지 않는다. 다른 해석만 추가/취소하며 서버는 해당 유형·조건과 출처를 확인한다. 반복·재열기는 무중복이고 자동 본문·다른 추가문·직접 편집을 보존한다.

기준을 직접 변경하면 두 코드와 수정하지 않은 자동 본문을 함께 갱신한다. 직접 편집·추가문은 보존하며 현재 유형과의 차이를 표시한다. 조회·초안 구성과 DB 저장은 분리하고 저장·PDF에서 현재 본문을 저장한다. 기존 저장본은 그 본문을 읽으며 자료 갱신·화면 재진입으로 초기화하지 않는다. 빈 본문을 최초 작성으로 간주해 다시 채우지 않는다.

기존 body/v1/v2·출처 사본·내부 묶음 정보는 호환에 사용한다. 사용자에게 묶음·단일/다중 모드나 새 작성 상태를 관리하게 하지 않는다. 필요한 최소 변경만 기존01~04에서 처리하고 서비스·문서·작업 단계를 추가하지 않는다.

## 수치와 분류

십진수 처리에는 Python Decimal을 사용한다. 원본 입력 수치와 분류에 적용할 반올림 값을 구분한다. 반올림을 선택한 경우 ROUND_HALF_UP 의미의 사사오입을 적용한다.

T점수 경계와 원문 자료의 조건은 고정된 비교 연산으로 평가한다. 자료에 실행 가능한 Python·SQL 수식을 입력하는 범용 규칙 엔진은 만들지 않는다.

사용자가 정한 공통 경계와 척도별 예외에서 현재 H/M/L을 산출하고, 기질·성격 코드는 정해진 척도 순서로 만든다. 자료에 적힌 유형표의 행 번호를 유형 식별자로 사용하지 않는다. 하나의 유형에 여러 해석을 저장할 수 있다.

## 최소 데이터 구성

기존 계정·일정·자료·보고서 구조를 재사용한다. 초기8개와 통합54개/추가1개는 별개다. 종전 TYPE-02/03과 TYPE-04 저장/출력 연결은 구현됐고 TYPE-04 저장 안내R1 보완의 독립 판정은 대기다. 이번 요구의 자료 기반 자동 사용 판정·실사용55개 등록·새 기록5개/PDF7개는 익스큐트 자체 검증을 마치고 독립 리뷰 대기다. 검사판 근거 미확인0/54는 출처 확인 현황이며 제품의 자동 포함 가능 수로 쓰지 않는다. 원문·조건·선택 당시 점수/기준 사본과 편집문을 연결하고 새 컬럼·보고서 이력은 추가하지 않는다.

| 데이터 | 내용 |
|---|---|
| 기본 계정 | 로그인 아이디, 비밀번호 해시 |
| 일정 | 날짜·시간, 제목, 메모, 선택적인 검사 보고서 연결 |
| 소스 | 제목, 저자·전문가명, 관점, 원본 파일명, 사용 여부 |
| 해석 항목 | 소스 연결, 원문 위치, 원문, 보고서용 설명, 항목·관점·적용 조건, 사용 여부 |
| 현재 보고서 | 대상 정보, 검사판·검사일, 점수, 분류 설정, 선택 내역, 편집한 본문, 전문가 의견, 생성·수정 시각 |

보고서 이름·검사일 같은 목록 필드는 일반 필드로 둔다. 점수 묶음·현재 분류 설정·순서가 있는 선택 내역은 JSONB로 보관할 수 있다. 전문가 자료 자체를 코드 상수나 하나의 보고서 템플릿에 박아 넣지 않는다.

TCI-06은 기존 composition v1에 선택적인 `output` 객체만 확장한다. `subscales`·`combined`·`summary` 세 boolean으로 추가 영역 포함 여부를 저장한다. 키가 없는 기존 v1은 내용이 있는 영역을 기본 포함하며 입력된 하위척도 원점수도 내용으로 본다. 명시적 표시 설정 저장은 이 객체와 수정 시각만 갱신하고 기존 본문·점수·기준·근거 사본을 보존한다. 새 테이블·컬럼은 추가하지 않는다.

해석 조건은 보고서 항목, 관점, 검사판, 관련 척도, 현재 H/M/L 또는 유형 코드, 필요한 수치의 하한·상한과 포함 여부 정도로 제한한다. 여러 조건이 있으면 모두 충족하는 후보를 표시한다. 다른 기준의 참고문은 별도 표시로 조회한다. 복잡한 추론 언어를 추가하지 않는다.

각 수치 조건에는 원점수·원본 T점수·분류 적용 T점수·백분위 중 비교할 값을 명시한다. 기본 T점수 조건은 원본 값으로 비교한다. 분류 적용값을 명시한 조건만 반올림 결과를 사용한다. 미입력 값이 필요한 조건은 불충족으로 처리한다. 백분위 조건을 T점수 조건으로 환산하지 않는다.

후보 조회는 DB의 현재 소스·해석 내용을 읽는다. 기본은 관점과 수동 정렬값으로 정렬하며 임상적 우수성 점수를 자동 산정하지 않는다. 기본 상세 본문 전체와 순서를 유지하고 추가·대안의 첫2~3개 이후도 열람 가능해야 한다. 유사 묶음과 상충 표시는 자료에 지정한 값을 사용한다.

선택문과 출처 연결은 현재 보고서에 저장한다. 보고서 본문은 사용자가 작성·선택한 내용으로 유지하고, 소스 수정 때 다시 덮어쓰지 않는다. 보고서 수정 저장은 현재 레코드를 갱신하며 과거 버전 테이블이나 감사 이력 시스템을 추가하지 않는다.

TCI-UI-02에서는 주제·선택 묶음·설명 관계·기본 반영 위치를 자료와 연결하고 필요할 때 최소 필드만 추가한다. 선택 묶음과 보고서 위치를 분리해 위치를 옮겨도 같은 묶음의 선택 규칙과 원래 근거를 유지한다. 신규 근거는 서버의 자료와 검증된 후보 정보에서 구성한다.

기존 body·composition v1은 읽기 어댑터로 지원한다. 단순 GET에서 형식을 다시 저장하지 않고 기존 본문·근거·의견·출력 설정을 유지한다. 새 구조는 서버 검증·브라우저 상태·저장/복원·웹/PDF 조립을 함께 변경한다. 저장 형식 번호는 데이터 계약이며 보고서 버전 보관 기능이 아니다. 필요한 스키마 명령은 작은 재실행 가능한 추가 방식으로 제공하고 격리 PostgreSQL에서 검증한다.

UI-02의 자료 연결은 `interpretations.selection = {topic, group, relation, basis}` 또는 null이다. `section`은 기본 보고서 위치, `group_key`는 종전 유사 표시로 유지한다. 주제는 척도·유형·SC/일반 연계로 제한하며 관계는 common/additional/alternative, 근거는 원문 대조 설명이다. 빈 연결을 임의의 대체 묶음으로 추정하지 않는다.

composition v2는 종전 `sections`의 블록·의견·모드와 `output`을 보존하고 최상위 `group_modes` 및 블록의 `selection` 사본을 추가한다. 종전 항목 모드는 호환 정보이며 신규 선택 규칙은 `topic/group`별 모드다. 위치는 블록이 담긴 section으로 결정하고 원래 위치·점수·조건·출처는 evidence에 유지한다. 서명한 신규 연결 또는 저장 사본만 신뢰한다. 동일 본문의 복수 출처를 모으되 연결이 충돌하면 묶음을 미확인으로 둔다. 신규 동일 본문은 위치와 관계없이 한 번 선택한다. 과거 v1에서 서로 다른 항목에 이미 저장한 동일 설명은 본문 손실 없이 읽고 저장한다.

복수 출처의 교체 범위는 `topic/group`만 비교한다. 출처별 `relation/basis`가 달라도 같은 묶음을 유지하며, 주제·묶음이 실제로 다르거나 연결이 없는 출처가 섞이면 미확인으로 둔다. 카드와 선택 블록의 `selection`은 정렬상 첫 출처의 대표 정보이며 각 출처의 원래 관계·근거는 `evidence.members[].item.selection`에 모두 남긴다. 편집 요약에는 대표 관계임을 표시하고 상세에는 모든 출처의 선택 당시 관계·근거를 표시한다. 새 선택·위치 이동·순서 변경·제외로 편집기를 다시 그릴 때도 같은 사본을 읽으며 현재 자료로 덮어쓰지 않는다.

`upgrade-selection`은 nullable JSONB 컬럼만 추가한다. `link-initial-selection`은 내용이 최초 데이터와 같은 기존 8개 문단의 빈 연결만 보강하고 편집·중지·기존 연결을 건드리지 않는다. 두 명령은 재실행 가능하며 구현 당시 쓰기 검증은 격리 PostgreSQL 스키마에서 수행했다. 2026년 10월 23일 사용자가 [README](../../README.md)의 두 명령을 실행한 뒤 실제 DB의 컬럼 존재·연결 8/8개, 기존 화면·후보 연결 표시 정상화를 읽기 전용으로 확인했다. 기존 보고서 전체 행은 연결 보강 전후 동일하다.

## TYPE-01 자료 팩 등록

`data/type_interpretations.json`의 통합54개·추가1개, 전사162개·provenance·integration의 원문 위치/출처/문장 연결을 재사용한다. comparison_notes2개와 구57개 팩의 해당 잔존 행은 새 후보/초안에서 계속 제외하고 기존 행·저장 근거는 보존한다. unknown/reference 원값·본문·원문·source_sha256을 승격/교체하지 않는다. 기존 selection.group=type01-integrated와 common/additional 관계를 사용하고 새 자동 사용 판정을 계산한다. seed-type-library의 기본 읽기 전용 점검과 --apply 누락 키 등록을 재사용하며 기존 편집/중지/필드 차이는 자동 갱신하지 않는다. 이번 사용자 지시로 익스큐트가 실사용의 누락 통합54개·추가1개를 등록했다. 필요한 소스는 이미 있어 추가0개이며 기존 scope 차이4개와 행을 보존했다. 재등록0·실사용 자동 포함54/54를 확인하고 독립 리뷰를 기다린다. 검사판 근거 확인 집계와 제품의 실제 등록/자동 사용 집계를 구별한다.

## 자료 업데이트

자료 관리 화면의 저장으로 소스·해석 항목을 갱신한다. 데이터 추가마다 프로그램 코드를 변경하거나 배포하지 않는다. 첫 버전에서는 별도 캐시를 두지 않고 새 조회에서 최신 내용을 읽는다.

현재 우선 작업은 네 소스를 대조해 기질27·성격27의 실제 기본 상세 본문과 확인된 추가·대안을 수록하는 것이다. 모든 이론·하위척도·연계 전수 수록과 구별한다. 관련 척도와 유형, 관점, 조건을 함께 연결한다. 원본의 반복 설명과 서로 다른 해석은 여러 후보로 등록할 수 있다.

원본 PDF·PPT·HWPX는 자료 정리의 입력이다. 제품 사용자가 파일을 올리기만 하면 의미 분류와 해석 추천까지 자동 완성하는 변환 파이프라인은 첫 제품에 넣지 않는다. 추가 자료는 텍스트 입력·붙여 넣기와 간단한 연결 설정으로 수록한다.

## PDF 출력

Playwright Python의 Chromium으로 현재 보고서 HTML을 PDF 바이트로 생성해 다운로드한다. PDF를 별도 서버 보관함에 쌓는 기능은 만들지 않는다.

웹 보고서와 출력용 CSS를 함께 관리한다. A4 세로, 배경 색상 출력, 한국어 폰트, SVG 마커, 긴 문장과 페이지 나눔을 확인한다. 폰트는 Windows 설치 폰트에만 의존하지 않고 Linux에서도 동일하게 사용할 수 있는 한국어 폰트를 지정한다.

PDF는 저장 성공 후 같은 보고서 데이터로 만든다. 저장에 실패하면 편집 내용을 화면에 유지하고 저장 오류를 표시한다. PDF용 HTML에도 실제 적용 경계·반올림·척도별 예외와 참고문 구분을 포함한다. 폰트 로딩이 끝난 뒤 출력하여 한글과 줄바꿈을 확인한다.

PDF 생성에 실패해도 현재 보고서 내용은 유지하고 다시 시도할 수 있어야 한다. 단일 서버에서 실행하는 짧은 동기 요청으로 시작하며, 별도 작업 큐는 도입하지 않는다.

TCI-07 구현은 Playwright 1.64.0·대응 Chromium 156.0.8078.4(revision 1248)를 고정한다. `report_body.html`과 기존 `read_model`을 웹/PDF가 공유한다. 로컬 Noto Sans CJK KR Regular·Bold/OFL 1.1을 포함하고 인쇄 시 data URL로 전달한다. 자체 로그인 URL을 HTTP로 다시 열지 않는다. 폰트 로딩과 실제 custom font 사용을 확인하며 외부 네트워크 요청을 차단한다.

저장 트랜잭션에서 검증·커밋한 독립 사본을 전달하고 생성 중 트랜잭션을 유지하지 않는다. Flask 동기 요청 안에서 Playwright async API를 실행해 전체 45초 제한과 context/browser 닫기 각 5초 제한을 적용한다. 저장된 PDF만 재시도하는 GET은 쓰지 않는다. `page.pdf()`의 바이트를 A4 세로·print_background·prefer_css_page_size·명시적 여백으로 내려보낸다. 설치 명령·폰트 출처와 Windows 검증 결과는 README 및 TCI-07 실행 보고서에 있다. Linux 실제 실행은 미확인이다.

PDF만 재시도하는 링크는 문서를 이동하지 않는 GET 다운로드로 처리한다. 현재 미저장 설정·이탈 보호 기준선을 변경하지 않으며 PDF 재시도 후 추가 편집의 새로고침 경고를 유지한다. 열린 웹 본문이 마지막 미리보기라는 안내와 재열기 동작은 현재 저장 사본과 구별한다.

## 개발 및 실행 환경

Windows 로컬에서 작성·확인하고 GitHub로 코드를 관리한다. 실제 운영 환경은 AWS의 Ubuntu 24.04 서버 1대이며, 같은 Python·DB 계열과 의존성으로 동작하게 한다. 환경별 DB 접속값과 파일 경로는 설정으로 분리한다. Ubuntu 24.04는 [Playwright의 지원 환경](https://playwright.dev/python/docs/intro)에 포함된다. 구현 시 해당 Playwright 버전의 Chromium과 운영체제 의존성을 함께 설치한다.

현재 제작 목표는 기능과 사용성 검증이다. 기본 로그인은 포함하며, 사용자별 자료 접근 권한·보안 강화·백업·복구·운영 자동화와 다른 프로그램 확장은 설계·구현 범위에서 제외한다. 이 제외 항목을 첫 제품 제작의 선행 작업으로 추가하지 않는다.

## 필요한 확인

분류 경계·반올림·유형 순서·PS 처리와 함께 추가 클릭 없는 통합 본문 출력, 다른 해석의 추가·취소·무중복, 기준 변경 후 직접 편집 보존·재열기·PDF를 확인한다. 초기 자료의 실제 내용을 이용해 후보 연결을 검산한다. 화면에는 실제 후보를 넣어 사용자가 보고서를 끝까지 작성할 수 있어야 한다.

로그인·로그아웃, 두 대시보드의 이동, 최근 검사 검색·리뷰·이어 작성, 일정의 등록·수정·삭제도 확인한다.
