상태: active · R2~R8 보완·자체 검증·독립 검수 통과 · 운영 미적용 · 관리: 공통 기반 · 갱신: 2026-10-29

## 2026-10-29 추가 보완 계약 · R6~R8

사용자의 개선 지시로 R6~R8을 구현했다. 새 기능·스키마·필수 작성 단계는 추가하지 않았다. 전체 326건·브라우저 11개 흐름·독립 19건 검증과 호환성/운영 상태는 [PLAT-20261029-03](../changes/platform.md#plat-20261029-03)에 기록한다.

- R6: K-HTP 작성 화면이 시작된 계정과 현재 로그인 계정을 구분한다. 다른 계정이면 신규 업로드·저장·자동 재전송을 차단하고 현재 입력/그림을 보존한다. 같은 계정 재로그인은 안전하게 세션 토큰을 갱신하여 재시도할 수 있다. 토큰 갱신과 실제 쓰기 사이 계정 전환도 서버에서 확인한다. 기존 원본의 소유권 검사와 읽기 공유 범위는 유지한다.
- R7: TCI/K-HTP 검사 메모·댓글 신규/수정의 SQL 실패에서 DB 재조회 없이 제출한 본문·공개 범위·수신자·원래 처리 경로를 복구 폼에 보존한다. DB에서 확인된 정보로 표시하지 않는다. 재시도 시 현재 접근권·작성자·CSRF를 다시 검사한다. HTML을 이스케이프하고 기존 검사/메모/공유를 바꾸지 않는다.
- R8: 공통 대상자 검색 입력의 Enter는 부모 저장 폼을 제출하지 않는다. 입력 검색·Escape·Tab 이동·결과 버튼의 Enter 선택은 유지하고 결과 첫 항목을 자동 선택하지 않는다. 일정/TCI/K-HTP에 같은 기준을 적용한다.

소유권: K-HTP 서버/편집 화면/JS는 R6, `tci_web/collaboration.py` 및 검사 댓글 복구 템플릿은 R7, `static/people.js`는 R8을 담당한다. DB 형식·모델·PDF 내용·원본 자료·아이콘 영향 없음. 코드/템플릿/JS를 함께 복구하며 이미 잘못 저장된 자료를 자동 재귀속하지 않는다. 격리 회귀/실제 브라우저와 구현 후 순차 독립 리뷰를 수행한다.

API 계약: K-HTP 편집기는 서버가 계정 ID에 서명한 `X-KHTP-Draft-Context`를 모든 요청에 고정 전달한다. 서버는 전달된 컨텍스트의 서명/형식/현재 계정을 검증하고 불일치 시 `409, code=draft_account_mismatch`를 반환한다. `/current`는 새 컨텍스트가 유효하면 동일 계정의 세션 갱신을 허용한다. 컨텍스트 없이 CSRF 헤더만 전달한 경우 현재 토큰과 일치해야 하며 옛 JS의 무조건 갱신을 차단한다. 헤더 없는 직접 API bootstrap과 유효 CSRF 호출 호환은 유지하며 이 값이 검사 소유/공유 권한을 부여하지 않는다. 배포 전 옛 화면의 세션 변경 복구에는 입력 보관 후 새 화면이 필요하다.

수정 전 추가 검수에서 R6~R8을 재현한 [발견 기록](../changes/platform.md#plat-20261029-review-03)은 보존한다. 현재는 위 계약으로 보완했고 독립 검수 범위 내 추가 필수 수정은 0건이다. 아래 R2~R5 완료 기록은 해당 보완 범위로 유지한다.

<a id="recovery-fixes"></a>
## 2026-10-29 후속 검수 보완 계약

사용자의 수정 지시로 R2~R5를 보완했다. 새 기능·스키마·필수 화면은 추가하지 않았다. 아래는 현행 계약이며 실제 검증·독립 리뷰·운영 상태는 [후속 수정 대장](../changes/platform.md#plat-20261029-02)에 기록한다.

- R2: 일반 검사 편집에서 대상자 코드가 바뀌면 같은 소유자의 연결 일정 중 대상자가 명확하게 다른 일정의 검사 연결만 같은 트랜잭션에서 해제한다. 일정의 대상자·시간·제목·내용·공유·댓글은 유지하고 revision/updated_at을 갱신한다. 해제 건수를 저장 안내에 표시한다. 다른 소유자의 일정은 변경하지 않으며, 대상자 미연결 일정은 임의로 재귀속하지 않는다. 기존 불일치 데이터는 조회 시 잘못된 검사 정보/링크를 숨기고 일정 소유자에게 확인 안내를 표시한다. 병합 경로의 기존 전체 연결 이동은 유지한다.
- R3: 기존 검사 연결의 현재 비노출 상태와 사용자의 명시적 연결 해제를 구분한다. 편집 폼의 `__keep__`는 해당 소유 일정에 이미 저장된 연결을 유지한다는 뜻이며 ID/권한을 새로 부여하지 않는다. 신규 일정이나 다른 검사로 연결하는 권한 우회에는 사용할 수 없다. 기능 OFF/공유 회수 시 검사 메타데이터는 숨긴다. 연결 유지 중 대상자를 변경해 불일치를 만드는 요청은 해제/재선택 안내와 함께 거절한다.
- R4: K-HTP 업로드·저장·분석 및 PDF 실패 복구에 필요한 응답용 대상자 요약을 해당 저장 트랜잭션 안에서 준비한다. 요약 준비가 실패하면 기록/순번도 롤백하고, 저장 완료 이후의 별도 요약 조회로 성공을 failed로 바꾸지 않는다. 저장된 ID·개정·내용과 응답 사본은 같은 저장 결과를 가리킨다.
- R5: 일정 수정의 최초 조회가 실패해도 제출한 제목·날짜·시간·소요 시간·상태·내용·연결 선택·개정을 DB 재조회 없이 복구 화면에 유지한다. 재시도는 현재 소유권·CSRF·개정을 다시 검증한다. 저장된 내용을 조회했다는 의미로 제출값을 표시하지 않는다.

공통 연결 정리의 구현 원본은 `tci_web/schedule_links.py`, 호출자는 TCI 점수 저장과 K-HTP commit_edit이다. 일정 조회/편집/복구는 scheduler.py·관련 템플릿, 응답 준비는 khtp_web/__init__.py, 사용자 안내는 각 저장 응답/화면이 소유한다. 기존 재현 4건을 회귀 검증에 추가하고 독립 재검토한다.

후속 검수(2026-10-29)에서 위 네 문제를 재현한 [수정 전 기록](../changes/platform.md#plat-20261029-review-02)은 보존한다. 보완 후 전체 311건·격리 PostgreSQL 보완 25건·실제 브라우저 보완 4개/기존 7개 흐름을 통과했다. 순차 독립 검수 29건도 통과했으며 검토 범위 내 추가 필수 수정은 0건이다. 아래 최초 구현 검증 결과는 당시 확인 범위다.

<a id="scope"></a>
## 범위와 흐름

PLAT-PEOPLE / PLAT-SCHEDULE. 최신 사용자 지시에 따른 변경 계약이다. 검사 작성 중 기존 대상자를 검색·선택하거나, 처음 입력한 이름·관리번호·날짜로 저장하면서 대상자를 생성한다. 별도 등록 절차를 선행시키지 않는다. 저장한 검사에서 `일정 잡기 → 날짜·시간 확인 → 저장`으로 연결한다. 일반 일정에는 대상자가 없어도 된다.

대시보드에는 TCI, K-HTP, 스케줄러 세 영역을 둔다. 게시판, 공개 예약 링크, 자동 리마인더, 결제·그룹·반복 예약은 이번 구현에 포함하지 않는다. 회원 관리와 기능 ON/OFF는 공통 관리 기능이며 관리자도 다른 계정의 개인 자료를 자동 열람하지 않는다.

<a id="identity"></a>
## 대상자 식별·병합

- 내부 기본키와 계정 안의 순번을 구별한다. 계정별 `code:0001`부터 발급하고 9999 이후에는 자릿수를 늘린다. 이름·관리번호·날짜가 같아도 자동 병합하지 않는다.
- 대상자는 `owner_id, code, name, reference, registered_on, merged_into_id`를 가진다. 관리번호·날짜는 각 검사에도 기존대로 저장하며 보고서의 스냅샷을 덮어쓰지 않는다.
- 새 대상자 발급과 검사 저장은 같은 트랜잭션이다. 기존 대상자 선택은 같은 계정의 ID만 허용한다. 다른 계정에서 공유받은 검사의 대상자 전체 이력에는 접근할 수 없다.
- 병합은 같은 계정의 두 대상자를 명시적으로 선택하고 코드·이름·이동할 검사/일정 수를 확인한 뒤 실행한다. 남길 대상자의 코드·정보를 유지하고 기존 코드는 병합 안내용으로 보존한다. 연결만 옮기고 검사 내용, 소유권, 공유, 댓글을 바꾸지 않는다.
- 기존 검사는 대상자 미연결 상태를 유지한다. 이름·관리번호를 근거로 일괄 연결하지 않는다. 편집 화면에서 기존 대상자를 선택하거나 새 대상자로 저장한다.

<a id="schedule"></a>
- 병합 시 동시 편집 보호를 위해 TCI 저장 기준시각과 K-HTP·일정 revision을 갱신한다. 보고서 본문은 변경하지 않는다.

## 일정 계약

- 기존 PostgreSQL `appointments`에 `person_id, job_id, duration_minutes, status, revision, updated_at`을 추가한다. 기존 `day, time, title, note, report_id, owner_id`는 보존한다. 기준 시간대는 Asia/Seoul이다.
- 신규 소요 시간은 60분을 기본으로 30분·60분 및 직접 입력을 제공한다(5~1440분). 종료 시간은 시작+소요 시간으로 계산한다. 기존 소요 시간은 NULL(미설정)로 보존하고 편집 저장 때 명시한다.
- 상태는 예정/완료/취소. 날짜 이동으로 미래·과거 일정에 접근한다. 잘못된 입력·저장 실패·개정 충돌 때 입력을 보존한다.
- 일정은 선택적으로 대상자와 TCI 또는 K-HTP 한 검사를 연결한다. 같은 대상자의 다른 기록은 권한을 확인한 이력에서 연다. 공유받은 검사를 자신의 일정에 연결할 수 있지만 원 소유자의 대상자 연결을 가져오지 않는다.
- 개인 일정 관리는 겹친 시간을 금지하지 않고 겹침을 안내한다. 공유받은 일정은 자신의 예약 가능 시간 판정에 자동 포함하지 않는다. 소요 시간 미설정은 종료 시각을 계산하지 않는다. 공개 자동 예약은 미구현이므로 예약 가능 시간을 보장한다고 표시하지 않는다.
- 읽기 공유와 작성자별 댓글/개인 메모는 `appointment_shares`, `appointment_comments`에 저장한다. 검사 공유 테이블의 기존 제약을 바꾸지 않는다. 수신자는 일정 수정·삭제·재공유 불가. 댓글은 소유자↔개별 수신자 대화이며 개인 메모는 작성자에게만 보인다. 회수 후 댓글 접근도 차단한다.
- 연결 검사와 대상자 이력은 별도 권한이다. 일정을 공유해도 검사·다른 일정·대상자 전체 이력을 자동 공개하지 않는다. 검사 접근권이 없거나 회수되면 해당 링크와 메타데이터를 숨긴다.

<a id="management"></a>
## 관리자와 기능 설정

`users.is_admin`은 관리자 여부, `is_active`는 사용 상태, `session_version`은 기존 로그인 무효화 기준이다. 공개 가입은 항상 일반 활성 회원으로 생성한다. 첫 관리자는 운영자가 `set-admin --username <기존 아이디>`로 지정한다. `/admin`의 회원 목록은 검색·페이지 이동과 사용 중지/활성화만 제공하며 검사·일정 내용은 조회하지 않는다. 자신의 계정 및 마지막 활성 관리자 중지는 막는다. 상태 변경 시 세션 개정을 증가시켜 중지 기간에 사용하지 않은 이전 로그인도 재활성화 후 재사용하지 못한다.

`feature_settings(key,enabled)`는 tci/khtp/schedule 전역 사용 설정이다. 기본 ON, 관리자만 CSRF 검증 후 변경한다. OFF는 메뉴뿐 아니라 직접 URL·API·저장·그림·PDF·연결 이력도 차단한다. 자료는 삭제하지 않고 재활성화하면 기존 권한으로 접근한다. 공통 출처/해석자료 편집은 관리자만 허용하며 열람·검사 선택은 기존 계약을 유지한다.

OFF는 해당 기능 UI/API의 사용 중지이며 데이터 동결은 아니다. 공통 대상자 병합은 사용 중지된 기능의 연결 ID·충돌 보호용 개정도 함께 정리한다. 같은 소유자의 연결만 변경하고 본문·점수·그림·공유는 보존한다. 병합 확인의 건수는 이동 범위를 알리는 정보이며 기능 내용 열람을 허용하는 것은 아니다.

| 공통 선택 UI | `templates/person_picker.html`, `static/people.js`, `static/people.css` | 같은 계정 검색/코드 표시, 별도 필수 등록 화면 없음 |

대상자 서비스는 `resolve_person(connection, owner_id, person_id, name, reference, registered_on, create=True)`로 정규 ID를 반환한다. `GET /people/search?q=`는 `{items:[{id,code,name,reference,registered_on}]}`를 반환한다. 코드 문자열은 4자리 이상이다. 상세·병합은 소유자만 접근한다. 새 대상자 생성은 이름 또는 관리번호가 있을 때만 허용한다.

## 검증·영향·복구

UI/DB/API/권한/공용 사용처 변경 있음. 생성 파일 형식·검사 계산·본문·원본 자료 변경 없음. 스키마 준비는 명시적 CLI로만 수행하고 앱 시작 시 DDL은 실행하지 않는다. 운영 및 실사용 DB에 이번 작업이 직접 적용되지 않는다.

검증: 계정 격리, 중복 코드 방지, 같은 이름 별도 등록, 기존 선택, 병합 보존, 일정 양쪽 검사 연결, 공유 회수, 댓글 분리, 입력 오류 유지, 동시 편집 충돌, 과거/미래 이동, 관리자 권한·기능 차단, 기존 unittest 및 격리 화면 검증. 전체 unittest 286건 통과(82.943초), 독립 집중 검증 50건·필수 수정 0건. 격리 PostgreSQL 18.6에서 동시 코드 발급/병합/반복 이관과 일정 20건 검증을 통과했다. 브라우저 7개 통합 흐름·390px 화면·TCI PDF 4쪽/K-HTP PDF 5쪽을 확인했다. 일정 댓글 저장 실패 복구 R1도 재검토했다. 자세한 결과·제한은 [공통 변경 대장](../changes/platform.md#plat-20261029-01)에 기록한다.

복구: 서비스 중지 후 이전 코드와 배포 전 DB 백업을 함께 복원하는 방식이 완전 복구다. 추가된 필드·테이블을 삭제하는 자동 downgrade는 제공하지 않는다. 구버전 코드는 새 권한/대상자/공유 계약을 알지 못하므로 새 데이터가 생긴 뒤 코드만 되돌려 운영하지 않는다.

## 참고와 선택

[Calendly의 복수 소요 시간](https://calendly.com/help/how-to-set-up-multiple-durations-for-an-event-type)은 예약 길이 선택을, [Acuity의 중복 일정](https://help.acuityscheduling.com/hc/en-us/articles/16676952402957-Using-overlapping-appointments-and-double-booking-in-Acuity-Scheduling)은 겹침 허용 설정을 제공한다. 해석은 30·60분/직접 입력과 겹침 안내를 채택하고, 기존 일정에 알 수 없는 길이를 일괄 부여하지 않는다. 기본 60분은 해석 내부 일정의 초기값이며 두 서비스의 보편 기본값이라는 뜻이 아니다.

[Calendly의 일정 설정](https://calendly.com/help/scheduling-faq)과 [Acuity의 예약 가능 시간](https://help.acuityscheduling.com/hc/en-us/articles/16676883635725-Managing-availability-and-calendars)은 소요 시간과 가능 시간을 별도로 관리한다. 이번에는 내부 일정 관리에 필요한 시작·소요 시간과 날짜 이동만 채택한다. 개인 미팅을 사용자가 직접 입력하므로 겹침은 안내하고, 자동 예약·버퍼·영업 시간 설정은 추가하지 않는다.
