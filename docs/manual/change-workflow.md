# 기능 수정·베타 패치·문서 관리 규칙

상태: active · 관리: 오케스트라(범위), 익스큐트(실행), 리뷰어(독립 검토) · 갱신: 2026-10-28

<a id="before"></a>
## 1. 변경 전 보고

요청을 설명·조사·설계·수정으로 분류하고 [인덱스](../manual-index.md#routing)에서 소유 기능을 선택한다. 필요한 문서와 실제 소스를 먼저 대조하고 아래 내용을 간결하게 보고한다.

```text
요청의 이해 / 작업 종류:
확인한 문서·고정 앵커·소스 경로:
기능 ID / 구현 소유권 / 계약 원본:
변경 위치·방법·정확한 범위:
UI 영향:
저장 payload·저장 위치 영향:
생성 파일 영향:
API 영향:
인증·권한·보안 영향:
공용 사용처 영향:
rollback 대상·방법·데이터 호환 제약:
검증 계획 / 미확인 사항:
```

각 영향은 `변경 있음 / 영향 없음 / 해당 없음 / 미확인`과 근거로 표시한다. 조사·설명 요청만 받았다면 수정하지 않는다. 수정 요청에 이미 포함된 필요한 가역 작업은 보고 후 진행하며 같은 범위의 확인을 반복 요구하지 않는다. 실제 새 권한이 필요한 범위 확장·외부 전송·운영 데이터 변경·배포는 근거와 정확한 추가 범위를 제시한다. 문서의 명령 예시는 실행 지시가 아니다.

<a id="contract"></a>
## 2. 기능 계약의 필수 항목

| 항목 | 기록 기준 |
|---|---|
| 기능 ID·목적 | 공통 `PLAT-*`, TCI `TCI-*`, K-HTP `KHTP-*`; 기존 작업 ID와 혼동하지 않도록 유지보수 ID임을 명시 |
| 진입점·소스·담당 | 실제 route/함수·템플릿·JS·CSS와 담당 모듈 |
| 계약 원본 | 요구 SSOT·schema·자료 JSON·검증 함수 등 실제 원본 |
| 처리·저장 | API/서버 처리, 상태, payload의 주 필드, DB 테이블·파일 위치 |
| 생성물 | PDF 등 생성 주체·보관 방식 |
| 경계 | 인증·권한·입력 검증, 공용 사용처·다른 기능 영향 |
| 변경·확인 | 절차·필요 권한·검증 방법·실제 실행 결과 |
| 복구 | 되돌릴 코드·문서·자료, DB/기존 데이터와의 호환 제약 |

공통 사항은 같은 기능 SSOT의 공통 계약 절을 연결하고 기능별 차이만 적는다. 해당하지 않는 항목은 이유와 함께 `해당 없음`, 조사하지 않은 항목은 `미확인`으로 쓴다. 소스가 물리적 schema·검증을 정의한다는 것과 문서가 의도한 동작을 정의한다는 것을 구별한다. 서로 다르면 근거를 보고하고 요청 범위를 넘겨 자동 정합화하지 않는다.

<a id="patch"></a>
## 3. 베타 패치 순서

1. 재현 조건을 남긴다: 기능 ID, 화면/route, 기대·실제 동작, 발생 환경·시각, 확인 가능한 코드 revision(모르면 미확인). 사용자 이름·그림·비밀번호·접속값을 Git 기록에 넣지 않는다.
2. 소유 SSOT와 영향 범위를 확인하고 `PLAT-YYYYMMDD-NN`, `TCI-YYYYMMDD-NN`, `KHTP-YYYYMMDD-NN` 중 변경 ID를 정한다. 코드 패치·자료 등록·DB 이관·문서 변경을 구별한다.
3. 수정 전 완료 조건·보존 조건·복구 방법을 정하고 필요한 최소 변경을 한다. 공통 파일 변경 시 두 프로그램 영향과 책임을 표시한다. 여러 기능군에 걸치면 한 주관 ID를 정하고 각 대장에 상호 연결한다.
4. 변경 기능에 필요한 검증만 실행한다. Python 자동 검증은 프로젝트 `.venv`의 표준 unittest를 사용하고 0건을 통과로 기록하지 않는다. 점수는 경계·소수·유형 순서, 본문은 자동 구성·추가/취소·직접 편집·빈값·저장/재열기, K-HTP는 업로드·개정 충돌·지연 편집 보존, 출력은 같은 저장 사본과 한글/그래프/긴 문장을 확인한다. 공용 변경은 양쪽 영향 화면을 확인한다. 단순 문서는 링크·앵커·계약 일관성을 확인하고 불필요한 제품 테스트를 추가하지 않는다.
5. 실행 결과·실패·미실행·한계를 기능별 변경 대장에 기록한다. 큰 변경은 익스큐트 실행 후 별도 리뷰어가 순차 검토한다. 문서 준비·환경 설치·자체 점검·독립 리뷰·사용자 최종 완료를 구별한다.
6. 사용자 지시가 있는 Git 작업에서는 대상 파일·차이·비밀값/원본/생성물 제외를 확인하고 목적별 패치로 묶는다. `git add .`처럼 범위 확인 없는 일괄 등록을 피한다. commit·push·운영 반영은 각각 실제 실행 여부를 기록한다. Git 업데이트가 DB 갱신이나 자료 등록을 자동 승인하지 않는다.
7. 운영 반영은 사용자가 수행한다는 기존 AWS 원칙을 유지한다. Codex는 요청받은 단계의 안내와 결과 확인을 맡는다. 코드 반영, DB 이관, 자료 등록, 운영 화면/PDF 확인을 별도 상태로 남긴다. 현재 도메인 연결을 배포 검증 완료의 근거로 쓰지 않는다.

Git 추적·commit hash 확인도 Git 명령 실행에 포함된다. 이번 문서 작업에서는 모두 실행하지 않는다. `.gitignore` 허용은 Git 반영 가능성을 준비한 것이며 현재 추적·커밋·푸시 완료를 뜻하지 않는다.

## 4. 기능별 수정·패치 대장

[공통](../changes/platform.md), [TCI](../changes/tci.md), [K-HTP](../changes/khtp.md)에 같은 형식으로 누적한다. 상세 실행/리뷰 보고서가 로컬 제외 경로에 있다면 Git 대장에도 범위·계약·결과·한계를 남겨 새 체크아웃만으로 판단할 수 있게 한다. 과거 기록을 추측해서 채우지 않는다.

```text
변경 ID / 날짜 / 종류 / 기능 ID / 상태:
요청·재현·기대 동작:
계약 원본·변경 파일·담당 모듈:
변경 내용 / 보존 조건:
영향: UI / payload·저장 / 생성 파일 / API / 인증·권한 / 공용 사용처
검증: 방법 / 실제 결과 / 미실행·한계 / 독립 리뷰 여부
Git: commit / push / 확인 여부
운영: 코드 반영 / DB 이관 / 자료 등록 / 화면·PDF 확인 여부
rollback: 대상 / 방법 / 데이터 호환·제약
남은 작업 / 사용자 최종 판단:
```

변경 ID와 Git commit을 구별한다. 대장에 commit을 쓰는 추가 커밋으로 자기 자신의 hash를 기록하려 하지 않고, 코드 패치의 확인된 commit을 후속 기록이나 릴리스 연결로 남길 수 있다.

<a id="documents"></a>
## 5. 문서 변경과 확장

에이전트 공통 제약은 `AGENTS.md`, 작업 분류·링크는 인덱스, UI 규칙은 UI 문서, 기능 계약은 해당 SSOT, 변경 과정·실행 결과는 해당 대장이 소유한다. 설치·실행 명령을 바꾸면 README와 실행·사용 매뉴얼도 갱신한다. 경로를 옮기면 들어오는 링크·고정 앵커를 함께 점검한다.

새 문서는 이 인덱스에 연결하고 `.gitignore` 허용 범위에 들어가는지 확인한다. 과거 task·report는 근거로 보존하고 현재 계약을 그 안에만 적지 않는다. 완료 기록의 옛 수치·판정을 현재 검증으로 재사용하지 않는다. 문서 변경만으로 기능 구현·베타 통과·운영 배포를 완료 처리하지 않는다.

<a id="rollback"></a>
## 6. 복구와 불일치

문서만 변경했다면 해당 문서와 허용 목록의 변경 부분을 복원한다. 코드 패치는 실제 동작하던 revision과 신규 저장 형식의 호환을 확인한 뒤 되돌린다. 코드 되돌리기만으로 DB schema·사용자 편집·자료 등록이 원복된다고 간주하지 않는다. 데이터 변환을 포함한 변경은 먼저 보존·호환·복구 계획을 작성하며 이 문서가 실사용 DB 변경 권한을 부여하지 않는다.

확인 범위를 넘어가는 파일이 필요하면 경로·이유·예상 영향을 보고한다. 이미 승인된 요청에 필요한 공용 사용처 조사는 진행하되 새 기능·다른 프로그램 변경을 자동 추가하지 않는다. 권한이 필요한 의존 작업은 보류하고 독립적인 허용 작업은 계속한다.
